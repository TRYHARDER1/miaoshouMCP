## 2. 风险、推断与未验证项

**已确认问题：外发资料过量。** Muse 已拿到实际图片后，只需 assetId、对应文件名、处理角色和要求即可逐张处理。原图 URL、SKU Map Key、sourcePath、snapshotId/planId/batchId、ossMd5、原始全局 sequence、绝对本机路径、结果链接登记都不是处理图像的必要输入。SKU 标识可能反映内部商品结构，不能将其自动等同于密码，但没有外发必要。

**条件性高风险：签名 URL。** 代码会原样保留未来来源的查询参数。如果某 URL 带有访问签名、令牌或有效期，交出原 URL 可能同时交出访问能力。当前 12 个样本没有这类参数，不能据此说其他快照没有风险；也没有证据表明这些包已经实际上传给 Muse、发生了 AppSecret 泄露。属于交付边界缺陷，不能将“文件里有 URL”写成“已发生外部泄露”。

`.gitignore` 忽略 `.data` 解决版本库误提交的一部分风险，不能防止人工误发目录。JSON 编码只解决字符转义，不做数据最小化。删除查询参数会破坏签名语义且仍暴露来源，不推荐。

## 4. 推荐最小修正方案（待批准）

采用**同一内部 job 的新增安全交付投影**，不改已有 jobVersion=1、历史模板和包。新增独立目录 `.data/muse-deliveries/DELIVERY-{deliveryId}/`，只含 `manifest.json`、`prompt.md`、`images/{assetId}.{ext}`。不要把它嵌入旧 JOB 目录作为“整包可外发”目录，也不包含内部文件、符号链接或递归指向原目录的引用。

交付 DTO 仅有 `deliverySchemaVersion=1`、`policyVersion=muse-safe-v1`、不透明 deliveryId、market、language，以及 assets[].{assetId,fileName,roles,instructions,deliveryOrder}。这些是**交付投影版本**，不是数据库 job.version=2。新 Prompt 仅据此生成，不调用旧 MusePromptBuilder，也不要求 Muse 理解 SKU Key。

交付流程：只读取并校验已发布内部包 → 按白名单构造投影 → 从已验证的本地 original 复制所需文件并核对摘要，不联网 → 构建专属临时目录 → 原子发布。deliveryId 可按 jobId+policyVersion 确定性派生，生成时锁住同一内部 job；已存在且摘要一致直接复用，损坏明确拒绝，不覆盖。投影写出后不改内部链接/状态。建议新增 `product_image_export_muse_delivery(batchId)`，仅返回交付目录与安全 DTO；旧 export 工具继续作为内部管理接口，不能冒充已安全脱敏。

**数据库影响：推荐方案无 DDL 变更。** 交付投影可由固定内部包和策略版本重建，交付包元数据放自身目录即可。没有修改或复制业务映射到新表；本地仍凭同一 assetId 查回所有 SKU 关联。若将来要求持久化多次实际外发审计，另立需求，不冒充当前零表方案具备审计能力。

不推荐直接升级旧 job 到 v2：当前约束与唯一键不支持，且 inspect 强依赖旧 Prompt，迁移影响显著大于一个安全投影。是否最终采用新增工具/独立目录，需要用户批准。
